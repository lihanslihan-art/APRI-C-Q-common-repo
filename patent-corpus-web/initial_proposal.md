# 专利语料检索服务与起草工作台 — 初始提案

> 状态：初始提案（待实施）
> 日期：2026-09-17
> 作者：lihanslihan-art
> 范围：把一套现有的「无线通信研究 → 专利起草」Agent 工作流，改造成可本地部署的网站服务。

---

## 1. 背景

上游是一个 **Claude Code Agent 工作区**（私有仓库，需授权访问；仓库地址与访问方式记录在本地运维笔记，不在本文档中）。
它不是一个常规应用：整个仓库没有任何 LLM 客户端代码，也没有任何 Web 框架，没有
`requirements.txt` / `package.json` / `pyproject.toml` / `Dockerfile`。

它的「程序」是自然语言提示词，「运行时」是 Claude Code：

| 层 | 形态 | 可独立运行 |
|---|---|---|
| 情报侦察（7 个技术域 + 社媒 + 招聘） | 提示词 + 源清单 YAML + 去重状态 JSON | 否，需 Agent |
| 专利 / 商业秘密分流 | 纯文字判据 | 否，需 Agent |
| **先行技术检索语料** | **Python 标准库脚本 + 已入库倒排索引** | **是** |
| 硬件在环验证 | 提示词 + 硬件探针脚本 | 否，需专用硬件 |
| 起草（幻灯片 + 交底书） | Agent 现场编写 Python 构建器 | 否，需 Agent |
| 展示 | 2 个静态 HTML 查看器 + 1 个本地 Python 表单服务 | 是 |

**关键结论：全仓库唯一确定性、可直接产品化的资产是先行技术检索语料层。** 其余各层的能力都寄生在
Agent 会话中。这个事实决定了下面所有方案的形态。

## 2. 实测基准

以下数字全部在目标部署机上实测，不是估算。

### 2.1 语料规模

| 项目 | 数值 |
|---|---|
| IEEE 标准语料 | 55 份标准，约 17,800 页 |
| Wi-Fi 8 / TGbn 工作组语料 | 2,767 份文档，2,761 份有全文 |
| 已抽取纯文本总量 | 100 MB |
| 可检索页面总数 | 47,077 页 |
| 现有 JSON 倒排索引 | 59 MB（已入 git，可重建） |

### 2.2 部署机内存约束（决定性）

| 指标 | 数值 |
|---|---|
| 总内存 / 可用 | 3,499 MB / 1,209 MB |
| 已有常驻服务（微信 Agent 网桥） | 346 MB，峰值 520 MB |
| 现有 JSON 索引常驻两套 | **607 MB** |
| SQLite FTS5 替代方案常驻 | **14 MB**（磁盘 173 MB） |
| 每个 headless Agent 进程 | 283 MB |

可用内存只有 1.2 GB，且已有一个 346 MB 的常驻服务。**把 59 MB JSON 索引常驻内存会膨胀到 607 MB，
占掉一半可用内存，在这台机器上不可接受。**

### 2.3 检索方案对比（已建原型实测）

FTS5 原型对全量 47,077 页建库耗时 4 秒，库文件 173 MB。

| 查询形态 | 现有 JSON 索引 | SQLite FTS5 |
|---|---|---|
| 单词 | ~900 ms | 5.1 ms |
| 短语 | ~1,000 ms | 2.7 ms |
| 布尔 AND | 不支持 | 2.5 ms |
| 布尔 NOT | 不支持 | 4.5 ms |
| 前缀通配 | 不支持 | 4.4 ms |
| 全量命中计数 | 需全表扫 | 0 ms |
| 常驻内存 | 607 MB | 14 MB |

现有脚本每次调用都要 `json.loads` 整个 30 MB 索引文件，这是 900 ms 的来源。
FTS5 内存省 43 倍，单查询快约 200 倍，并且内置 `snippet()` 直接产出带高亮的上下文片段。

**结论：检索层必须走 SQLite FTS5，不是优化项而是默认项。**

## 3. 四个候选方案

| 方案 | 内容 | 工作量 | 是否需模型额度 |
|---|---|---|---|
| A | 静态阅读站：把现有查看器从 `file://` 改 HTTP 托管 + 定时重建 | ~1 天 | 否 |
| **B** | **检索 API + 轻前端：把语料层做成服务** | **2–4 天** | **否** |
| C | 全流程 Web 工作台，服务端自带 LLM，提示词二次实现 | 1–2 周 | 是 |
| **D** | **Headless Agent 作后端：原样驱动现有提示词** | **3–5 天** | **是** |

方案 A 价值有限，可作为 B 的半天热身。方案 C 只在将来需要对外多用户、单会话模型撑不住并发时才值得走，
其最大风险是起草环节目前靠 Agent **为每个专利现场编写构建器代码**，这个自由度无法直接映射到固定模板引擎。

## 4. B 与 D 的详细对比

### 4.1 服务的动作不同

- **B 服务「查」**：输入查询词，输出引证。把 2,822 份标准文档从命令行资产变成检索服务。
- **D 服务「写」**：输入一个模糊想法，输出完整起草产物。把提示词工作流变成 Web 工作台。

两者处于流水线的不同层，**不是替代关系**。

### 4.2 依赖成熟度差一个量级

| | B | D |
|---|---|---|
| 所需资产是否已存在 | 100%，逐项验证可跑 | 部分缺失 |
| 缺口 | 无 | 硬件在环设备不可用；上游配套的公开知识库仓库未随仓库分发，去重步骤会踩空 |
| 模型额度消耗 | 零 | 每次起草一整轮 |

### 4.3 交互模型是两种完全不同的 Web 架构

| | B | D |
|---|---|---|
| 单次延迟 | 2–5 ms | 空转 3.24 s；真实起草分钟到小时级 |
| 后端形态 | 普通 REST + 分页 | 任务队列 + 流式进度 + 断点恢复 + 人工闸门 |
| 前端形态 | 一个搜索框 | 长任务面板 |

D 的工程量**八成花在会话编排和并发隔离上，不在模型调用上**。

### 4.4 并发冲突是 D 最被低估的坑

上游所有提示词流程都假设**单会话独占文件系统**：

- 表单向导只有一份全局状态文件，没有按用户或 run 分命名空间，两人同时填表互相覆盖。
- 侦察流程的去重状态是全量重写，决策日志是追加写。
- 侦察流程会自动 `git commit` 并 push 两个仓库，并发跑必然产生 git 冲突。

要做多用户，必须给每个会话开独立 git worktree 或容器。**B 全程只读语料，零冲突，天然可并发。**

### 4.5 失败模式的可测试性相反

- **B 失败** = 查不到或查错，可复现、可写单元测试、可回归。
- **D 失败** = 模型输出漂移，同输入两次结果不同，传统断言兜不住。

上游作者对此有认识，配了两道兜底：强制的对抗性批判与应答循环，以及一个机器校验脚本检查配色和字号上限。
**做 D 时这两道必须保留为服务端自动化检查，不能因为上了 Web 就跳过。**

### 4.6 并发容量

按 283 MB/进程、可用 1,209 MB 算，D 最多支撑 **2–3 个并发会话**，且这是空转估算。
B 走 FTS5 只占 14 MB 可忽略。反之若 B 坚持 JSON 索引常驻，607 MB 一压，D 只剩 1 个并发位。

### 4.7 对上游仓库的侵入性

| | B | D |
|---|---|---|
| 侵入性 | 彻底旁路，只读语料目录，上游一行不改 | 提示词不改，外包一层会话编排 |
| 上游 `git pull` 冲突 | 无 | 无 |
| 需额外适配 | 无 | Windows 假设：文件监听需换 inotify/watchdog；旧版 Office 文档解析需换 LibreOffice headless（因文本已全量入库，仅新增旧格式文档时触发） |

## 5. 决策：先 B 后 D，B 是 D 的工具端点

这是最关键的一点。上游起草流程的**第一道强制闸门就是先行技术检索**，并要求任何新一代标准相关主张都必须
先查框架文档、再查意见处理文档、并引用工作组文档号。这一步现在是 Agent 去 shell 里跑检索脚本。

**B 上线后，D 里的 Agent 直接调 B 的 HTTP 接口**，单次从 900 ms 降到 5 ms，且能一次批量查十几个词而不必付
十几次进程启动代价。

所以落地顺序不是权衡而是**依赖关系**：

```
B（检索服务，2–4 天，零模型额度，独立可用产品）
   └─► D（起草工作台，3–5 天，把 B 当作先行技术检索工具端点）
```

如果只做一个，做 B。如果要的是完整的「专利生成网站」体验，D 不可省。

## 6. B 方案技术设计

### 6.1 架构

```
上游语料目录（只读）
  ├── ieee_standards/{text,toc}/*.json      55 份标准
  └── wifi8_tgbn/{text,toc}/*.json          2,761 份文档
            │
            │  build_db.py（幂等，4 秒全量重建）
            ▼
     corpus.db  ← SQLite + FTS5，173 MB，常驻 14 MB
            │
            │  FastAPI（uvicorn，单进程）
            ▼
     REST API : 3014
            │
            ▼
     前端：搜索页 + 文档阅读页
```

### 6.2 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/search` | 主检索。参数 `q`、`mode`(token/phrase/boolean/prefix)、`corpus`、`kind`、`topic`、`ballot`、`year`、`limit`、`offset` |
| GET | `/api/doc/{doc_id}` | 文档元数据 + TOC |
| GET | `/api/doc/{doc_id}/page/{n}` | 单页全文 |
| GET | `/api/facets` | 可用的 kind / topic / ballot / year 取值与计数 |
| GET | `/api/stats` | 语料规模与建库时间 |
| GET | `/healthz` | 健康检查 |

检索结果每条返回：`corpus`、`doc_id`、`title`、`kind`、`page`、`snippet`（带高亮标记）、`rank`、
以及首次公开日期（用首次披露版本而非最新修订版本，这是先行技术判定的正确基准）。

### 6.3 关键实现约束

1. **建库脚本必须幂等**，支持 `--corpus` 增量重建，输出到 `corpus.db.tmp` 后原子替换。
2. **FTS5 查询串必须转义**。带连字符的词如 `co-tdma` 在 FTS5 语法里会被解析成列名，必须加引号，
   否则报 `no such column`。这是原型阶段实际踩到的错误。
3. **过滤字段走 UNINDEXED 列 + 普通表 join**，不要塞进 FTS 索引，避免索引膨胀。
4. **只读挂载语料目录**，服务进程对上游仓库无写权限。
5. **绑定 127.0.0.1**，经反向代理暴露，不直接开放端口。

### 6.4 部署

| 项 | 值 |
|---|---|
| 端口 | 3014（3000 / 3008 / 3009 / 3010 / 3012 / 3013 已占用） |
| 进程管理 | systemd user unit |
| 注意 | nvm 下 node 为 v24，`/usr/bin/node` 为 v20；systemd unit 必须显式写 `Environment=PATH` 与绝对路径。已有的网桥 unit 就是靠这个绕开的，照抄 |

## 7. D 方案后续要点（本期不实施）

1. 每会话独立 git worktree 或容器，解决 4.4 的状态冲突。
2. 任务队列 + SSE/WebSocket 流式进度，保留提示词里既有的人工闸门。
3. 并发上限硬编码为 2，超出排队，避免 OOM。
4. 保留对抗性批判循环与产物机器校验为服务端自动步骤。
5. 先行技术检索改为调用 B 的 API。

## 8. 风险与未决项

| # | 项 | 状态 |
|---|---|---|
| 1 | **上游仓库不可镜像到公开仓库**：上游为他人所有的私有仓库，无 LICENSE，且含 55 份 IEEE 标准的抽取全文（受版权保护的商业出版物）。本仓库为 PUBLIC，因此本次只提交本提案与 B 方案自有代码，不镜像上游内容。 | **待用户决策**，见下 |
| 2 | 上游配套的公开知识库仓库未随上游分发，两个静态查看器缺少数据源 | 影响 A/D，不影响 B |
| 3 | 起草层依赖 `python-pptx` / `python-docx` / `matplotlib` / `PyMuPDF`，部署机未安装 | 影响 D，不影响 B |
| 4 | 硬件在环设备不可用 | 影响 D 的验证环节，可降级跳过 |

### 关于第 1 项的三个可选做法

1. **把本仓库改为 private**，然后镜像上游全量内容。最省事，但会影响本仓库现有的公开 POC 用途。
2. **建一个独立的 private 镜像仓库**，本仓库用 git submodule 指向它。保持公私分离，推荐。
3. **只镜像可公开部分**，剔除 IEEE 标准抽取全文与竞赛材料，保留脚本与工作组公开文档。工作量最大。

在用户明确选择之前，上游内容保持仅存在于部署机本地，不进入任何公开仓库。
